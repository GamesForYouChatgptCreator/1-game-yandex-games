# Tile Puzzle Home MVP для Unity WebGL и Яндекс Игр

## Резюме для запуска

Для **первой релизной версии** `Tile Puzzle Home` не нужно изобретать новый жанр. На Яндекс Играх уже представлены triple-tile и mahjong-проекты с базовой формулой «нажимай верхние плитки → собирай тройки → проигрыш при заполнении 7 слотов», а рядом существует и спрос на «уютные» и jigsaw-пазлы. Это означает, что конкурентное преимущество MVP должно быть **не в правилах core-геймплея**, а в **мягкой ежедневной мета-прогрессии**: `5 побед → сундук → кусок пазла → новый фон` с уютной атмосферой и без наказания за пропуски. citeturn10search1turn10search9turn10search2turn10search7turn10search3

Такой выбор особенно хорошо совпадает с аудиторией платформы: по официальной странице Яндекс Игр для разработчиков, **58% аудитории — женщины**, а крупнейшая возрастная группа — **55+ (38%)**; ещё **15%** приходится на **35–44** и **11%** на **45–54**. Для этой аудитории MVP должен избегать штрафного обнуления прогресса, таймеров, агрессивной рекламы и перегруженного UI; лучше работают крупные элементы, короткие понятные сессии и визуально ощутимый прогресс. citeturn12view0

На уровне платформы обязательны четыре вещи: игра должна работать **без обязательной авторизации**, прогресс при этом нужно сохранять; авторизацию можно предлагать только после **осознанного действия** игрока; звук должен останавливаться при сворачивании страницы; реклама должна вызываться **только через SDK Яндекс Игр**, показываться в логических паузах и в rewarded-формате быть добровольной и ясно объяснять награду. citeturn22view0turn22view2turn5view4turn23view0

Для Unity Web релизная сборка должна быть ориентирована на **малый размер**, потому что Unity прямо связывает большой initial download с ростом bounce rate. В Unity 6 для Web рекомендуются `.NET Standard 2.1`, `IL2CPP Code Generation = Optimize for code size and build time`, `Managed Stripping Level = High`, низкий `Quality Level`, `Brotli` для релиза и, для действительно маленьких 2D WebGL-сборок, удаление неиспользуемого кода через **Web Stripping Tool**. citeturn14view5turn21view0turn21view1turn19view0turn21view3

### Что именно стоит выпускать

Релизный MVP должен состоять из **одного режима**, **50 уровней первой кривой**, **6 типов плиток**, **7-слотовой панели**, **5 пазлов**, **5 открываемых фонов**, **rewarded-only монетизации**, локального сохранения для гостя и облачной синхронизации для авторизованного игрока. Более сложные вещи — бустеры с экономикой, интерстициалы, монеты, магазин, ежедневные streak-штрафы, live-ops и серверная часть — лучше исключить из первой версии как лишний риск по сроку и качеству.

## MVP и краткий геймдизайн

### Состав MVP

Ниже — состав **первой публикуемой версии**, а не идеальной игры.

| Включить в MVP | Почему это нужно в релизе |
|---|---|
| Bootstrap/Loading с SDK init и `LoadingAPI.ready()` | это влияет на метрику Game Ready и обязательную интеграцию SDK citeturn6view0turn5view3 |
| Главное меню | точка входа, текущий прогресс пазла, кнопка «Играть», «Коллекция», «Настройки», мягкая кнопка авторизации |
| Экран игры | единственный основной цикл: поле 7×7, 7 слотов, пауза, прогресс к сундуку |
| Экран награды | после 5 побед: сундук, кусок пазла, анимация постановки |
| Экран коллекции | выбор открытого фона |
| Настройки/пауза | звук, музыка, выход в меню |
| 50 уровней | достаточно для первой кривой удержания и теста баланса |
| 5 пазлов × 5 фонов | достаточно, чтобы daily-loop был осязаемым |
| Rewarded-реклама | добровольная и понятная награда соответствует требованиям платформы citeturn22view0turn23view0 |
| Локальное сохранение гостя | требуется платформой, даже без авторизации citeturn22view0turn5view1 |
| Облачное сохранение для авторизованных | даёт продолжение между устройствами через `Player`-данные citeturn8view0turn5view0 |
| Базовая аналитика | нужна, чтобы понять, прошёл ли MVP точку first-session fit |

| Исключить из MVP | Почему это лучше отложить |
|---|---|
| Интерстициалы | пользовательский стресс выше, а у вас уже есть rewarded-only стратегия |
| Монеты и магазин | усложняют мету, UI и баланс без критической пользы для первого релиза |
| Покупки | не нужны для проверки core/META fit; к тому же платежи в Яндекс Играх должны идти только через SDK citeturn22view0 |
| Бустеры с отдельной экономикой | легко раздувают scope и делают баланс хрупким |
| Сложные блокеры, таймеры, PvP | не нужны для проверки гипотезы «уют + прогресс + возврат» |
| Обнуление прогресса за пропуск дня | это плохой fit для взрослой casual-аудитории; вместо этого нужен freeze-policy |
| Addressables как обязательная часть MVP | Unity рекомендует их для больших Web-проектов, но при маленьком объёме контента они увеличивают сложность без гарантированного выигрыша; для 5 фонов и 50 уровней лучше сначала уложиться в лёгкую сборку, а адресуемую загрузку отложить до момента, когда build size реально станет проблемой. citeturn19view0turn14view5 |

### Core loop и meta loop

**Core loop** должен быть очень коротким и очень понятным:

`увидел доступную плитку → нажал → плитка ушла в слот → 3 одинаковых исчезли → поле стало чище → либо победа, либо риск переполнения слотов`

Это полностью совпадает с уже знакомой игрокам жанровой схемой на Яндекс Играх, где страницы проектов описывают именно очистку поля и проигрыш при заполнении 7-слотовой панели. citeturn10search1turn10search9

**Meta loop** для MVP:

`5 побед сегодня → сундук → 1 кусок текущего пазла → при завершении пазла открывается фон → фон автоматически становится активным`

Это и есть основной источник возвратов. Его задача — не «фарм», а **ежедневно показываемый визуальный прогресс**.

### Daily limits и политика пропусков

Для retention-friendly MVP я рекомендую **мягкий дневной лимит мета-прогресса**, а не лимит игры:

| Параметр | Решение для MVP |
|---|---|
| Играть уровни в день | без жёсткого лимита |
| Засчитываемые победы в дневной сундук | первые 5 побед за календарный день |
| Награда за сундук | 1 кусок пазла |
| Дополнительная rewarded-возможность | 1 дополнительный кусок не выдавать; вместо этого давать `shuffle` или `continue after fail` |
| Пропуск дня | **заморозка**, а не обнуление |
| Смена дня | по локальной дате устройства, с защитой от простого «скролла времени» через сравнение `lastSeenUnix` и `server time`, если позже добавите сервер; в MVP можно ограничиться локальным сравнением и не обещать античит |

Почему именно freeze-policy: платформа требует, чтобы прогресс сохранялся сразу и не терялся от обновления страницы, а сама аудитория Яндекс Игр заметно взрослая; к этому лучше подходит «жалко пропускать», чем «страшно потерять». citeturn22view2turn12view0

### Монетизация

В этой версии нужна только **rewarded video**, потому что Яндекс рекомендует показывать рекламу после действия пользователя, rewarded-размещение не ограничивает по частоте, а rewarded-награда должна быть добровольной и ясно объяснённой. citeturn5view4turn23view0turn22view0

Три допустимых rewarded-placement’а для MVP:

| Placement | Текст кнопки | Награда | Комментарий |
|---|---|---|---|
| После проигрыша | `Посмотреть рекламу и продолжить` | очистить 2 последних слота | дополнительный бонус, а не обязательное продолжение |
| Перед тупиком | `Посмотреть рекламу и перемешать` | безопасный shuffle | снижает фрустрацию |
| После завершения пазла | `Посмотреть рекламу и оживить фон` | включить анимированную версию фона на сессию | эмоциональная награда вместо валюты |

### Сохранения и данные игрока

У Яндекс `player.setData()` допускает до **200 КБ** данных на игрока, а `player.setStats()` — до **10 КБ** числовых данных; частота вызова ограничена, поэтому облачные операции нужно батчить и не дёргать после каждого тапа. Для локальной WebGL-копии Unity `PlayerPrefs` хранится в IndexedDB браузера и имеет лимит **до 1 МБ**, чего для MVP более чем достаточно. citeturn7view0turn7view1turn15search2

Минимальный save-payload:

| Поле | Тип | Назначение |
|---|---|---|
| `saveVersion` | int | миграции формата |
| `currentLevelIndex` | int | текущий уровень |
| `winsToday` | int | прогресс до сундука |
| `lastDailyResetDate` | string | `YYYY-MM-DD` |
| `currentPuzzleId` | string | активный пазл |
| `currentPuzzleUnlockedPieces` | int[] | какие куски открыты |
| `completedPuzzleIds` | string[] | завершённые пазлы |
| `unlockedBackgroundIds` | string[] | доступные фоны |
| `selectedBackgroundId` | string | активный фон |
| `audioEnabled` | bool | звук |
| `musicEnabled` | bool | музыка |
| `firstSessionCompleted` | bool | для аналитики и онбординга |
| `authOffered` | bool | чтобы не спамить приглашением войти |

### Онбординг первых трёх минут

Ниже — рекомендуемый flow, чтобы игрок без текста понял игру.

| Время | Что происходит | Цель |
|---|---|---|
| 0:00–0:20 | Bootstrap, SDK init, `LoadingAPI.ready()` | быстрый старт и корректная platform markup citeturn6view0 |
| 0:20–0:40 | Главное меню, выделена кнопка `Играть` | минимум выбора |
| 0:40–1:20 | Уровень 1: подсветка трёх одинаковых плиток и слотов | показать действие |
| 1:20–2:00 | Уровень 2: без подсветки, но с мягким hint через 4 секунды бездействия | закрепить правило |
| 2:00–2:40 | Уровень 3: появляется второй тип решения, игрок сам собирает 2–3 тройки | дать ощущение самостоятельности |
| 2:40–3:00 | показать прогресс `3/5 до сундука` и превью пазла | сформировать короткую цель возврата |

В онбординге лучше **не** использовать длинные тексты. Достаточно 1–2 карточек по 3–5 слов: `Нажимайте плитки`, `Три одинаковых исчезают`, `Не заполняйте все 7 слотов`.

## Дизайн уровней и система пазлов

### Базовые правила уровня

Для этой версии берём следующую базовую механику:

| Параметр | Значение |
|---|---|
| Поле | 7×7 якорных ячеек |
| Типов плиток | 6 |
| Слотов в лотке | 7 |
| Победа | поле очищено |
| Поражение | в слоты помещено 7 плиток и ни одна тройка не схлопнулась |
| Время | без таймера |
| Слои | от 1 до 3 по мере роста сложности |
| Доступность | в начале уровня должно быть доступно минимум 5 верхних плиток |

Жанрово это опирается на уже знакомый для игроков паттерн Яндекс-каталога с 7 слотами и очисткой поля; отличие `Tile Puzzle Home` — не в core rule, а в уютной и ежедневной мета-системе. citeturn10search1turn10search9

### Генератор уровней

Для **первых 50 уровней** я рекомендую не полностью случайную генерацию, а **template-based generator** с валидацией. Это заметно надёжнее для MVP.

Алгоритм:

1. Выбрать шаблон маски уровня: какие клетки 7×7 заняты и какая у каждой глубина стека.
2. Выбрать число активных типов плиток по целевому диапазону сложности.
3. Сформировать пул плиток так, чтобы количество каждого типа было кратно 3.
4. Ограничить стартовую «угрозу»: в первых 7–9 выдаваемых верхних плитках должно быть не больше 4 разных типов.
5. Разложить плитки по стеку обратным порядком открытия.
6. Прогнать валидацию:
   - deterministic bot находит хотя бы один путь до победы;
   - random solver делает не менее 50 прогонов;
   - если уровень проваливает тест, пересобрать.
7. Сохранить seed и шаблон в `LevelDefinition`.

Практически это означает: у вас **данные уровня фиксированы**, но их можно пересобрать или расширить, не переписывая код.

### Правила генерации

| Правило | Зачем |
|---|---|
| Общее число плиток кратно 3 | иначе невозможно завершить уровень |
| Каждый тип встречается минимум 3 раза | исключает «мусорные» одноразовые типы |
| На старте доступно минимум 5 плиток | уменьшает ощущение тупика |
| В первых 10 уровнях не более 4 типов | снижает когнитивную нагрузку |
| В первых 20 уровнях глубина стека не выше 2 | сохраняет читаемость |
| На любом уровне симулятор должен находить решение | исключает публикацию «битых» уровней |
| Не использовать специальные блокеры в первой версии | не раздувать scope |

### Система пазлов и фонов

Для MVP я рекомендую делать **не “картинку ради картинки”**, а **слоистый фон**, который постепенно оживает. На Яндекс Играх уже есть triple-tile, cozy и jigsaw-продукты — значит, связка пазла с уютным фоном даёт более понятную дифференциацию, чем ещё один клон с бустерами. citeturn10search1turn10search7turn10search3

#### Правила пазлов

| Параметр | Решение |
|---|---|
| Кусков в одном пазле | 6 |
| Как выдаётся кусок | после первого дневного сундука за 5 побед |
| Порядок открытия | псевдослучайный, но сначала углы/центр для заметного прогресса |
| Повторные куски | запрещены |
| Что при пропуске дня | прогресс **замораживается** |
| Когда открывается фон | сразу после 6/6 кусков |
| Что происходит после открытия | фон автоматически активируется |
| Можно ли потом менять фон | да, через `Коллекцию` |

### Сохранения

Для MVP лучший компромисс — **versioned JSON** в `PlayerPrefs` локально и тот же JSON как cloud-copy через `player.setData()`.

Почему так:

- Unity WebGL хранит `PlayerPrefs` через IndexedDB браузера и даёт до **1 МБ**, чего для маленького save-файла достаточно. citeturn15search2
- Яндекс позволяет сохранять пользовательские данные через `Player` и поднимать их между устройствами. `player.setData()` даёт до **200 КБ** и имеет лимит частоты, значит лучше пушить реже, а не после каждого действия. citeturn8view0turn7view0

Рекомендуемый формат:

```json
{
  "saveVersion": 1,
  "currentLevelIndex": 14,
  "winsToday": 3,
  "lastDailyResetDate": "2026-07-25",
  "currentPuzzleId": "puzzle_fireplace",
  "currentPuzzleUnlockedPieceIndices": [0,1,3],
  "completedPuzzleIds": ["puzzle_living_room"],
  "unlockedBackgroundIds": ["bg_living_room"],
  "selectedBackgroundId": "bg_living_room",
  "audioEnabled": true,
  "musicEnabled": true,
  "firstSessionCompleted": true,
  "authOffered": false
}
```

Сохранять локально нужно **сразу после значимого действия** — это соответствует и требованиям Яндекса к сохранению внутреннего прогресса. citeturn22view2

### Build settings

Unity рекомендует для Web следующие настройки: `.NET Standard 2.1`, `IL2CPP code generation` на кодоразмер/скорость сборки, `Managed Stripping = High`, низкий `Quality Level`, а для mobile Web — release build без development-флагов, `Disk Size with LTO`, `Brotli` и максимально маленький build size. Для Web также полезно удалить неиспользуемые shader variants и 2D-коду помочь через Web Stripping Tool. citeturn21view0turn21view1turn19view0turn21view2turn21view3

Рекомендуемая конфигурация именно для этого MVP:

| Настройка | Значение |
|---|---|
| Build Profile | Web |
| Development Build | Off |
| Code Optimization | `Disk Size with LTO` для release |
| API Compatibility | `.NET Standard 2.1` |
| IL2CPP Code Generation | `Optimize for code size and build time` |
| Managed Stripping | `High` |
| Web Compression | `Brotli` |
| Decompression Fallback | Off, если грузите архив на сервер Яндекса; On только если собственный хост не отдаёт корректные `Content-Encoding` |
| Name Files As Hashes | On |
| Quality | `Low` |
| Target WebAssembly 2023 | On |
| Use WebAssembly.Table | On для нового проекта без legacy-`dynCall()` плагинов |
| Native multithreading | Off |
| Run In Background | Off |
| Initial Memory Size | старт с 128 MB |
| Memory Growth | `Geometric` |

Почему `Run In Background = Off`: Яндекс требует останавливать звук при сворачивании страницы, а Web `Run In Background` в Unity разрешает продолжать работу при потере фокуса. citeturn24view0turn22view0

Почему `Use WebAssembly.Table = On`: Unity рекомендует включать его в **новых проектах**, если вы не зависите от старых `.jslib`, использующих `dynCall()`. citeturn24view0

### Минимальная аналитика и KPI

Официально найденные страницы Яндекс Игр для WebGL акцентируют `LoadingAPI`, `GameplayAPI`, рекламную статистику и метрики консоли, но не дают на поверхности готовой схемы custom gameplay events для такого MVP. Поэтому практически правильно сделать **два слоя аналитики**: обязательный platform markup для Яндекса и собственный `IAnalyticsService`, который сейчас пишет события в лог/локальный буфер, а позже сможет быть подключён к любому провайдеру. citeturn6view0turn5view2turn18search0

### Порядок реализации без лишних развилок

Самый безопасный порядок такой:

1. Сначала поднять **рабочую сборку WebGL** и SDK.
2. Потом доказать, что **одно поле и 7 слотов** ощущаются хорошо.
3. Затем сразу подключить **данные уровней**, чтобы не хардкодить кривую.
4. После этого добавить **сундук → пазл → фон**.
5. И только потом заниматься **авторизацией, облаком и rewarded**.
6. Последним этапом — **арт, аудио, аналитика и релизная упаковка**.

Такой порядок минимизирует риск, что в конце недели у вас будет красивая оболочка без работающего продукта.

## Итоговая рекомендация

Если цель — **не прототип, а первая публикуемая версия**, то правильный MVP для `Tile Puzzle Home` — это не “ещё одна игра про три плитки”, а **очень простой triple-tile с уютной ежедневной мета-наградой**, где игрок не получает стресс, но получает причину вернуться завтра. Это решение лучше всего согласуется и с текущей аудиторией Яндекс Игр, и с ограничениями rewarded-only монетизации, и с тем, как WebGL-проекты надо упрощать ради скорости загрузки и стабильности. citeturn12view0turn22view0turn14view5turn19view0
