CODEX MASTER SPECIFICATION
Проект: Tile Puzzle Home
Версия документа: 1.0
Назначение: единственный технический источник истины для Codex.
Движок: Unity 6000.3.20f1
Рендер: Universal Render Pipeline, 2D Renderer
Платформа: WebGL / Yandex Games
Язык кода: C#
Целевая ориентация: Portrait
Базовое разрешение интерфейса: 1080×1920
Репозиторий: https://github.com/GamesForYouChatgptCreator/1-game-yandex-games

================================================================================
0. РОЛЬ CODEX
================================================================================

Codex отвечает за:
1. Создание и изменение структуры Unity-проекта.
2. Создание папок.
3. Создание C#-скриптов.
4. Создание Editor-скриптов.
5. Создание сцен.
6. Создание и настройку объектов сцен.
7. Создание Prefab.
8. Создание ScriptableObject-классов и экземпляров данных.
9. Создание Sprite Atlas.
10. Настройку Project Settings через Editor API, где это возможно.
11. Перемещение импортированных художником ассетов в правильные папки.
12. Автоматическую настройку TextureImporter.
13. Проверку отсутствующих ссылок.
14. Создание тестовой сцены для визуальной проверки графики.
15. Поддержание проекта в собираемом состоянии после каждой задачи.

Codex не отвечает за:
1. Создание финальной графики.
2. Изменение художественного стиля.
3. Самовольное добавление механик.
4. Самовольную смену архитектуры.
5. Добавление сторонних пакетов без отдельного разрешения.
6. Изменение количества уровней, пазлов или фонов.
7. Усложнение MVP ради будущего масштабирования.

Главное правило:
После каждого завершённого задания проект должен компилироваться без ошибок.

1. ПРАВИЛА РАБОТЫ С ФАЙЛАМИ
================================================================================

Codex имеет право:
- создавать новые папки;
- создавать новые файлы;
- перемещать файлы;
- переименовывать файлы;
- удалять только созданные им временные файлы;
- создавать .meta-файлы через Unity;
- создавать Editor tooling для автоматизации.

Codex не должен вручную генерировать .meta-файлы текстом, если Unity может создать их сама.

Перед перемещением существующего ассета:
1. Проверить все ссылки через AssetDatabase.
2. Использовать AssetDatabase.MoveAsset.
3. Не использовать файловую систему напрямую для ассетов внутри Assets.
4. Проверить результат AssetDatabase.Refresh.
5. Не терять GUID.

Любое массовое действие выполняется через Editor-скрипт:
Assets/Editor/ProjectSetup/
или
Assets/Editor/ImportTools/

GameplayController:
- оркестрирует LevelSession;
- не знает конкретные Image/Text элементы;
- не создаёт плитки напрямую;
- использует BoardController, TrayController, WinConditionEvaluator.

LevelSession:
- хранит runtime-состояние текущего уровня;
- не сохраняется напрямую;
- создаётся при входе;
- уничтожается при выходе.

BoardRoot:
- world-space или screen-space должен быть выбран один раз.
Рекомендуется:
- игровое поле и плитки внутри Canvas в Screen Space Overlay;
- не использовать физическую сцену для простого tile match.
Если реализовано через UI:
BoardRoot должен находиться внутри SafeAreaRoot между TopBar и Tray.
В этом случае [World]/BoardRoot заменить на UI/BoardRoot.

Для MVP рекомендуется UI-подход:
- плитка = RectTransform + Image + Button/PointerHandler;
- координаты = anchoredPosition;
- сортировка = sibling index;
- анимации = RectTransform.

PuzzleRoomController:
- получает текущий PuzzleDefinition;
- отображает количество открытых деталей;
- запускает reveal-анимацию только для новой детали;
- после полного пазла разблокирует BackgroundDefinition;
- вызывает SaveService один раз после изменения прогресса.

Пазл MVP:
- 5 уровней на одну деталь;
- рекомендуется 5 деталей на один пазл при 25 уровнях и 5 пазлах только если награда выдаётся чаще.
Но ранее зафиксировано:
каждые 5 уровней = 1 деталь;
5 пазлов при 25 уровнях невозможно, если каждый пазл состоит более чем из одной детали.
Codex не должен самостоятельно исправлять это противоречие.
До отдельного решения:
- реализовать систему данных гибко;
- PuzzleDefinition содержит requiredPieceCount;
- LevelDefinition содержит puzzlePieceReward;
- не хардкодить количество деталей.

Правила:

Controller связывает Model и View.

TileModel — runtime-состояние экземпляра.
TileView — визуализация.

Алгоритм клика:
1. TilePointerHandler сообщает TileView.
2. TileView вызывает callback Controller.
3. BoardController проверяет доступность плитки.
4. TileModel отмечается выбранной.
5. TileView блокирует ввод.
6. Плитка анимируется в Tray.
7. TrayModel вставляет плитку в логически правильное место.
8. MatchResolver ищет тройку.
9. При совпадении удаляет три TileModel.
10. Проверяются win/lose.
11. Состояние View синхронизируется.
